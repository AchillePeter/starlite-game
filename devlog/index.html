Journal de développement

Devlog

StarLite II est développé en solo, comme un jeu navigateur d'un seul fichier. Voici les coulisses techniques — netcode, performance, rendu.

Optimiser le rendu des grandes nuées

Performance · moteur de rendu

Une nuée de 300 Zglenglo en mouvement est le pire cas que le moteur puisse affronter. Le cache de sprites est volontairement contourné pour les unités en déplacement (afin de garder l'animation de marche fluide), si bien qu'une nuée mobile retombe intégralement sur le tracé vectoriel procédural, image par image.

Le chantier en cours : un atlas de poses de marche (précalculer quelques images discrètes du cycle de marche au lieu d'un tracé 100 % procédural), plus une résolution de collision consciente de la densité. Ce sont les deux prochains gros gains pour ce scénario précis.

Un netcode lockstep déterministe

Multijoueur · réseau

Le duel en ligne repose sur un modèle lockstep déterministe : au lieu de synchroniser l'état complet du jeu, les deux clients n'échangent que les ordres et rejouent la même simulation, tick par tick. Cela suppose un déterminisme parfait — même générateur pseudo-aléatoire, même ordre de résolution, mêmes calculs de chemin.

Un relais WebSocket léger achemine les commandes ordonnées entre les pairs, et un système de sommes de contrôle périodiques permet de détecter toute divergence de simulation entre les deux machines.

Tout un RTS dans un seul fichier HTML

Architecture

StarLite II tient dans un unique fichier HTML — moteur, rendu, IA, netcode et données de jeu compris. Ce choix rend le déploiement trivial et le partage instantané : une seule page à mettre à jour. Le code est organisé en modules internes qui reproduisent une architecture classique tout en restant packagés dans ce fichier unique.
